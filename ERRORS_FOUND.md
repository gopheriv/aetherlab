## Second review pass (uncommitted lesson/produced-video work)

Found by close review of the changed-but-uncommitted surface (assembly, lesson
pipeline, cards) that the happy-path tests only smoke-check. Both fixed and
re-verified; full suite stays green.

| # | Severity | Feature | File | Defect |
|---|----------|---------|------|--------|
| BUG-6 | Rendering | F148 Produced lesson (crossfades) | `services/assembly.py:343` | `_xfade_chain` tracks `cum` so that `offset_k = cum - k*d` should equal the documented `sum(durs[0..k-1]) - k*d`. But it updated `cum += durs[k] - d`, **double-subtracting the overlap** — so from the 2nd crossfade on, each `offset` drifts earlier by an accumulating `d`, over-clipping mid-lesson segments (a ~10-segment lesson with `d≈0.5s` lands its final crossfade ~4s early). ffmpeg still runs (offsets stay monotonic), so the smoke test F148 passes while the produced lesson silently loses time. Fixed to `cum += durs[k]`; offsets now match the reference formula exactly. |
| BUG-7 | Logistical | F146/F147 Chapter aspects | `services/lesson_pipeline.py:314` | `_chapter_aspect` decided the "setup" (first-chapter) composition via `renderable[0].id == ch.id`. LLM-planned lessons routinely omit chapter ids (`LessonChapter.from_json` defaults `id=""`), so `"" == ""` tagged **every** id-less chapter as `setup`, collapsing the setup→evolution→math→recap arc for AI lessons (keyless lessons have hardcoded ids and were unaffected — why F147 passed). Fixed to compare by object identity (`renderable[0] is ch`), robust regardless of ids. |
| BUG-8 | Logistical / UX | F145 Lesson view (seek + subtitles) | `ui/widgets.py:3624`, `services/lesson_pipeline.py`, `services/assembly.py` | The produced lesson prepends a 3s intro card and inserts a 2.2s card before every chapter, then crossfades all segments — but the chapter-outline **seek offsets** and the **.srt** cue times were both computed as a plain running sum of raw chapter-clip durations from t=0. So clicking "Chapter 2" seeked into the *middle of Chapter 1* in the real video, and the error compounded (~9s off by chapter 3); subtitles drifted the same way. A regression from the produced-lesson work (before it, `assemble_lesson` did a plain concat and the naive offsets lined up). Additionally the UI indexed durations by *plan*-chapter index, mis-aligning whenever a lesson had a non-rendered `interactive` chapter. Fixed: `assemble_lesson(..., return_offsets=True)` reports each chapter clip's true start (shared `_segment_starts` with the xfade graph); `LessonBundle.chapter_offsets` carries them (cache-safe); the outline seeks and `build_srt(segments, starts)` use them; the UI walks rendered chapters with a separate index and falls back to a running sum for old caches. |
| BUG-9 | Logistical / UX | F143/F145 Partial lesson alignment | `services/lesson_pipeline.py:142,222`, `core/models.py`, `ui/widgets.py:3631` | If a middle renderable chapter failed, `run()` compacted successful `SceneBundle`s into `rendered`, then `_narrate_chapters()` zipped that compact list against the full renderable chapter list. A surviving later clip (e.g. Chapter 3) was narrated, titled, subtitled, and outlined as the failed earlier chapter (Chapter 2). Fixed by carrying `rendered_chapter_indexes` (plan indexes) alongside `chapter_scenes`/`chapter_offsets`, narrating from `(plan_index, chapter, scene)` tuples, and teaching `LessonView` to map offsets by plan index. Old caches keep the legacy fallback. |

## Fourth review pass (deep edge-case audit)

Found by targeted review of security, retrieval freshness, and cloud-render
race paths that normal happy-path tests do not naturally exercise. Fixed and
covered by regression assertions in `test_features.py`.

| # | Severity | Feature | File | Defect |
|---|----------|---------|------|--------|
| BUG-13 | Security / sandbox escape | F103 Scene code safety gate | `services/code_safety.py` | The safety gate blocked direct `open`, `eval`, and direct dunder attributes, but accepted string-based escape helpers such as `getattr(__builtins__, 'open')`, `getattr(type, '__subclasses__')`, and `().__getattribute__('__class__')`. Generated Manim code runs in a real Python subprocess, so this was an arbitrary file/host access bypass if an LLM produced adversarial code. Fixed by banning dynamic runtime-introspection helpers, `__builtins__`, `type`, more dunder attributes, and string-literal references to banned runtime handles. |
| BUG-14 | Retrieval correctness / stale data | F43 Library ingestion | `services/ingestion.py` | Incremental Chroma ingestion upserted changed files but never deleted old chunks for the same source path. If a file shrank or a PDF extraction changed, orphan chunks remained in the vector store and could keep appearing in RAG results forever, contradicting the current library contents. Fixed by deleting chunks with matching `path` metadata before re-upserting a changed file. |
| BUG-15 | Cloud render race / wrong artifact | F154 Cloud render | `services/render_backend.py` | GitHub `workflow_dispatch` usually returns no run id, so AetherLab polls branch runs by `job_id`. If no matching run had appeared yet, `get_run` returned the newest run on the branch (`runs[0]`). Under concurrent or recent renders this could attach to another job, download the wrong artifact, or report the wrong failure. Fixed so unmatched polls return queued until a run whose name/title contains this exact `job_id` appears. |

## Sixth review pass (cloud render never actually dispatched)

Found by reproducing the user report "REMOTE MODE UNAVAILABLE AND CLOUD RENDERING
TOO". The backend `available()`/`select_backend`/fail-soft logic was all correct;
the real blocker was that a correctly configured repo+token could still never
render. Fixed and covered by the F154 regression.

| # | Severity | Feature | File | Defect |
|---|----------|---------|------|--------|
| BUG-17 | Cloud render setup dead-end | F154 GitHub Actions cloud backend | `services/render_backend.py`, `ui/main_window.py`, `docs/CLOUD_RENDERING.md` | GitHub's REST `workflow_dispatch` only dispatches a workflow that exists on the repo's **default branch**, and the dispatched `ref` runs that branch's copy of the file. AetherLab committed only the scene (`jobs/<job_id>.py`) and **never installed `.github/workflows/render.yml`** into the user's render repo, so every dispatch 404'd ("workflow not found") — surfaced to the user as cloud/remote "unavailable" even with a valid repo + token. (The setup docs told users to add the workflow by hand, which most never did; the device-login token also needs the `workflow` scope, which was undocumented.) Fixed by bundling the workflow (`RENDER_WORKFLOW_YAML`), adding `provision_render_repo()` which installs it idempotently on the default branch AND the render branch (with a clear message when the token lacks the `workflow` scope), calling it before the first dispatch and from the Settings "Test cloud render" button (now a one-click provisioner), and documenting the `workflow` scope. |
| BUG-18 | Cloud render workflow always failed | F154/F158 cloud render workflow | `services/render_backend.py` (`RENDER_WORKFLOW_YAML`), `.github/workflows/render.yml` | **Found by a real end-to-end smoke** (provision → dispatch → poll → download against a live private render repo). The bundled workflow's `actions/setup-python@v5` step used `cache: pip`, which requires a `requirements.txt`/`pyproject.toml` to compute the cache key — a render repo has neither, so the step failed with *"No file matched to [requirements.txt or pyproject.toml]"* and **every cloud render failed before Manim was even installed**. Not caught by F154 (fully stubs GitHub) or F158 (only asserted the file's presence). Fixed by removing `cache: pip` (pip caching is pointless there — Manim is installed fresh each run), bumping `CLOUD_WORKFLOW_VERSION` 1→2 so job hashes refresh, and adding an F158 regression assertion that `cache: pip` is absent and the bundled constant stays byte-identical to `.github/workflows/render.yml`. Verified: the re-dispatched run succeeded and produced a valid 854×480 h264 MP4. |

| BUG-19 | Migration / UX | F153/F154 Cloud render settings | `core/settings.py`, `services/render_backend.py`, `docs/MANIM_BOT_SETTINGS_COMPAT.md` | The user's working `manim-bot/.env` had `CLOUD_RENDER_ENABLED=true` and a render repo, and `manim-bot` used GitHub CLI auth, but AetherLab only read process env/app config and required a pasted token. When launched from the desktop, the legacy `.env` and `gh auth login` session were invisible, so Cloud mode looked "unavailable" despite a configured worker. Fixed by adding a legacy `.env` fallback (`AETHERLAB_LEGACY_ENV_PATH`/`MANIM_BOT_ENV_PATH`, project `.env`, sibling `manim-bot/.env`; disabled by `AETHERLAB_DISABLE_LEGACY_ENV=1`) and a runtime `gh auth token` fallback. Tests use a fake `.env` and disable real legacy discovery so no real keys leak into automation. |
| BUG-20 | Cloud artifact download | F154 GitHub Actions cloud backend | `services/render_backend.py` | After provisioning and dispatch succeeded, MP4 download still failed with `HTTP Error 401` from the short-lived object-storage URL. The GitHub artifact/log endpoints return a 302 redirect; blindly following it can send the GitHub Bearer token to the signed storage host, which rejects the request. Fixed by handling the 302 manually, then fetching the signed URL without the GitHub Authorization header. Verified by a live cloud smoke: existing artifact downloaded to a valid local MP4. |
| BUG-21 | Visual regression reliability | F33/F135/F162 render cache + visual harness | `services/pipeline.py`, `services/manim_runtime.py`, `tools/visual_regression.py` | Strict visual regression initially failed all six scene cases with `FileNotFoundError` for MP4 paths under temp. The root cause was stale cached `SceneBundle(status="rendered")` rows whose `video_path` pointed at pruned/missing render files; the pipeline attempted to re-render, but the runtime skipped non-compiled bundles and left the stale path intact, so the harness reported a missing file instead of a clean rerender or true render failure. Fixed by downgrading missing cached rendered scenes to `compiled`, clearing stale video paths before render attempts and failed/skipped renders, and adding feature assertions. Re-verified with `python tools\visual_regression.py --out visual_regression\runs\today --compare visual_regression\baseline\current --strict`: 7/7 pass, 0 warnings, 0 regressions. |
| BUG-22 | Small-screen UX | F91 Command bar | `ui/widgets.py` | The command bar used a single horizontal row with fixed-width controls (`Examples`, quality, `Learn`, `Run`). At a 520px small-screen width the prompt input collapsed to a tiny sliver, making the primary task impossible even though buttons remained visible. Fixed by splitting the shell into an input row and an action row, preserving all controls while keeping the prompt field at a usable minimum width. Covered by F91. |
| BUG-23 | Cache poisoning / artifact validity | F34/F143 scene + lesson chapter caches | `services/pipeline.py`, `services/lesson_pipeline.py` | Scene and lesson chapter caches treated any existing MP4 path as reusable. A zero-byte, truncated, or replaced non-video file at the cached path could be reused as a successful render, surfacing later as a player/assembly/visual-regression failure instead of triggering a clean re-render. Fixed by upgrading `_video_exists()` to validate non-empty playable video streams (PyAV when available, size fallback only when PyAV is missing) and by routing lesson chapter cache checks through the same helper. Covered by F34 and F143. |
| BUG-24 | Doc-drift | F09 / US-F09 Qwen settings loader | `core/settings.py:129`, `build_feature_tracker.py` | The tracker described Qwen settings as automatic autoload, but `load_settings()` only applies `load_qwen_settings()` when `AETHERLAB_QWEN_AUTOLOAD=1`. The implemented privacy guard is correct, but the canonical feature copy implied a silent credential import. Fixed by renaming F09 to an opt-in loader and making the user story/expected behaviour match the code. Existing tests missed it because F09 only exercised the parser directly, while F128 separately asserted the gated default behaviour. |
| BUG-25 | Logistical | F34 / US-F34 UI solve cache video validity | `ui/workers.py:154`, `services/pipeline.py:116` | The headless pipeline rejected missing, empty, or unplayable cached rendered MP4s via `_video_exists()`, but the desktop `PipelineWorker` only checked `Path.exists()` before reusing a cached rendered scene. A corrupt non-empty MP4 could therefore be accepted in the real UI solve path while the headless smoke path correctly re-rendered. Fixed by routing the UI worker cache check and render decision through `_video_exists()`, clearing stale video paths before repair render, and extending F34 to assert `_scene_cache_usable()` rejects a fake MP4. Existing tests missed it because F34 only validated the shared helper, not the UI worker's separate reuse condition. |

## Seventh review pass (user-story Phase-2 audit)

Found by executing the F166–F168 user stories against their code paths with the
adversarial "fails mid-operation" variant rather than the happy path only.

| # | Severity | Feature | File | Defect |
|---|----------|---------|------|--------|
| BUG-26 | Logistical / data loss | F166 / US-F166 Lesson share bundle | `services/share_export.py:42` | `export_lesson_bundle` opened `zipfile.ZipFile(output_path, "w")`, which truncates the target immediately, and wrote every asset directly into it. Any mid-write failure (disk full, a missing/unwritable asset, a study-guide error) left a partial zip on disk — and because README/index.html/metadata/study_guide are written before the video, that partial zip still *opened* and looked plausible while missing the MP4, subtitles, and scenes. Re-exporting over a previously-good bundle destroyed it on failure. This is exactly the "misleading share bundle" the F166 failure-mode contract forbids. Fixed by staging into a sibling `<name>.part` file and `os.replace()`-ing onto the target only after the whole zip is written, unlinking the staging file on any exception. Existing test missed it because `t_f166` only asserted a successful export's contents, never a mid-write failure. Regression added to `t_f166`: a forced `_write` failure must leave the prior bundle byte-identical and leave no `.part`. |
| BUG-27 | Logistical / score corruption | F167 / US-F167 Course progress (quiz card) | `ui/widgets.py:3507` | `_QuestionCard._answer_mcq` was wired to `QRadioButton.toggled` and never locked the card, so it re-emitted `answer_recorded` on every selection change. A student who switched their answer — or clicked each option until "✓ Correct" appeared — recorded multiple attempts, and `CourseProgressStore` counts every attempt: the persisted `correct/attempts` score inflated and per-question miss counts grew with mere clicking, so the score reflected clicking behaviour rather than knowledge (e.g. "2/3" shown for a 2-question quiz). `CourseProgressStore` itself was correct; the corruption entered through the widget emit path. Fixed by recording only the first answer (an `_answered` guard) and disabling the radio group afterward. Existing tests missed it because `t_f167` called `_answer_mcq` exactly once and asserted a single emit, never a second selection. Regression added: a second `_answer_mcq` after answering must not emit again and the group must be disabled. |
| BUG-28 | Security / sandbox escape | F103 / US-F103 Scene code safety gate | `services/code_safety.py` | The gate allowlists `numpy`, but numpy's file-I/O surface is an arbitrary host read/write vector that no legitimate Manim scene uses and that needs **no** banned name or attribute: `ndarray.tofile(path)` / `numpy.fromfile` / `numpy.frombuffer(...).tofile(...)` write attacker-controlled raw bytes to an exact path (a write into a Startup folder is arbitrary-code-execution), `numpy.savetxt`/`loadtxt`/`genfromtxt` read/write exact text paths, `numpy.load(..., allow_pickle=True)` is a pickle-deserialization RCE, and `numpy.DataSource().open(url)` fetches remote URLs. All three probes passed the pre-fix gate as "safe". Since generated scene code runs in a real Python subprocess with full privileges, an adversarial LLM (or RAG-injected instruction) could exfiltrate or write host files. Fixed by adding a `BANNED_IO_ATTRIBUTES` sink set (tofile/fromfile/frombuffer/fromstring/fromregex/save/savez/savez_compressed/savetxt/load/loadtxt/genfromtxt/memmap/DataSource) rejected on attribute access, verified to leave legitimate numpy math and every bundled template/exemplar scene safe. Existing tests missed it because F103 only probed the classic dunder/`getattr` escape chains, never the allowlisted-library I/O surface. Regression added to `t_f103`. |
